Replaces the legacy cv-builder generation (`createAndGenerateCV` in `src/modules/cv/actions.ts`, `src/modules/cv/generate.ts`). The result is a **writing desk document** (Markdown with `:::` blocks), landed as a reviewable draft.

## Why replace it

Findings from the audit of the legacy pipeline:

- **One call writes the whole CV** (pass 4, `completeJSON`, 8000 max tokens). Quality and length are controlled only by prose in `src/lib/prompts/cv-generate.md`.
- **Over-production.** Only activities are capped (5/4/3 per role). Experiences, skills, tools, projects, certs and competencies are sent whole. The schema has no `.max`. The master CV narrative is injected *on top of* the full profile, and its prompt says to reuse all master outcomes. The pass-2 "must-include" tiers never reach the writing call.
- **No progress.** One blocking server action, a spinner and a static "15-30 seconds". `CVDocument.status = 'generating'` exists but nothing reads it.
- **Master CV saved nothing.** It adds tokens rather than replacing any.
- **Output is the legacy `CVDocumentContent` JSON**, not a desk document.

Attribution was already in place (`LlmUsageLog.jobApplicationId/cvDocumentId/runId`, `docs/llm-usage-tracking.md`). The gap is that `cvDocumentId` points at the legacy `CVDocument`, not a desk document.

## Decisions

1. **Master CV is dropped from job CV generation.** Evidence is curated per job from the profile. The master-CV generator (`career-vertical/master-cv.ts`) stays, and is kept for more generic recruiter handoffs.
2. **Deep dive is not required.** Strategy comes from the newest *complete* deep dive when one exists. Otherwise the Brief stage falls back to `JobApplication.jobAnalysis` (written from the early Jev assessment), and runs `analyseJob` only if that is also missing.
3. **One entry per employer, latest title, progression as sub-text, titles never changed** (phase 2b, from the first real preview run). Roles at one company are grouped into one employer entry (`employers.ts`). The CV heading is the LATEST title at that employer (a current role wins, otherwise the later START date, the end date only as the tiebreak: see Phase 3b); earlier titles appear only as a progression line built in code, oldest first, with neutral wording (`Three roles at Unity (2019–present): Program Manager → Technical Program Manager → Snr. Program Manager`; the dates are the employer's stints, so a returnee reads `2015–2017, 2019–present`, never one continuous span). Role titles are facts: no stage changes, merges or hides one, and the Brief's "play down" only affects emphasis and framing in descriptions and bullets, never a title or an employer. The profile does not record promotions, so the line never says "promoted".
4. **Bullets are relevance-driven, not recency-driven** (phase 2b). A total activity budget (14) is split across the employers that show bullets by the Select model's 1-5 relevance score per employer, proportionally, with at least 2 and at most 6 per employer, enforced in code after the model answers. The model still ranks activities within an employer. The per-role recency tiers 5/4/3 are gone: on a real profile three of the four bullet-bearing "roles" were consecutive roles at one employer, which spent most bullets on it while the lead-with employer got 2 of its 11.
5. **Claimed skills stay in the lists** (phase 3). A skill, tool or competency the profile lists with no evidence or certification behind it (`status: 'claimed'`) may appear in the Skills and Tools lists. It may appear in a bullet, the experience summary or the professional profile only when the job's requirements (the strategy's `mustHave` / `niceToHave`) name it; code scans the writers' output, retries that writer once with specific feedback, then accepts and logs a note (the run does not fail). A claimed name the candidate's own evidence text already contains is not claimed in effect and is not flagged. A claimed competency is never written into Core Competencies. A capability whose only backing is a certification that is still in progress counts as claimed here (the override is in the cv-generation evidence/candidate layer; profile-map still calls it `certified`). A claimed name of two characters or fewer ("C", "R", "Go") is matched case-sensitively and never next to `-`, `&`, `/` or an apostrophe, so it is not found in "C-suite", "R&D" or "go-to-market". Aliases are a **known gap**: a tiny best-effort map (GA4 / Google Analytics, JavaScript / JS, Kubernetes / K8s, PostgreSQL / Postgres) is the only equivalence code knows; anything else ("Tableau Desktop" for "Tableau") is not matched.
6. **Certifications and education are rendered by code, in relevance order, from the profile as stored** (phase 3). The profile has no status field, so status is read from the data (`write/status.ts`, computed once and reused by the renderer, the candidates, the evidence layer and the writers' name check). **Certifications:** in progress = an issue date in the future or in-progress wording in the name, written "(in progress)" and never presented as held; a past `expiryDate` means the certification has expired and it is **left off the CV** (log note "<name> expired in 2021 and was left out"); a future `expiryDate` is a held certification. **Education:** in progress = an end date in the future, in-progress wording in the qualification, field or grade, or **no end date and a start within the last 6 years** (`EDUCATION_RECENT_START_YEARS`); a past end date is completed (span and grade shown); **no end date and an older start** renders with no date span and no status (it never claims completion and never invents "in progress") and adds one lowest-priority check note asking the owner to add the end date. Brief and Select see "(in progress)" on such candidates, and the writers may not name a certification or qualification the evidence does not mention, nor an in-progress one without in-progress wording.
7. **Coach and verification flags stay rare** (phase 3). The log records at most three "worth a quick check" notes per run, only for genuinely risky items: a claimed tool used in a bullet because the job asked for it, or a figure that could not be matched to the profile after the retry, or an in-progress certification the text may present as held, or (lowest priority) an education entry with no end date. Notes are ordered by priority (invented figures, claimed tools, credentials, education dates) and then by employer order, not by completion order, and cut to three.
8. **Switch immediately.** "Generate CV" points at the new flow as soon as it ships; the old routes are then deprecated and removed in a follow-up.

## Pipeline

The model tiers below are recommendations. Feature code only names a `role` (`fast` | `default` | `analysis`); `ROLE_RECOMMENDATIONS` in `src/modules/llm/roles.ts` and the user's "Models by task" settings choose the model. No feature module names a model id.

| # | Stage | Role (model) | Purpose |
|---|---|---|---|
| 0 | Gather | none (code) | Profile snapshot, newest complete deep dive (`cvStrategy`, gaps, strengths) or `jobAnalysis` fallback, structure guide, block contract. |
| 1 | Brief | `analysis` (Opus) | The hidden question: what problem is this role hired to solve? Plus lead-with, emphasise, play down, per-section budget. Small JSON. |
| 2 | Select | `fast` (Haiku) | Chooses employers (with a 1-5 relevance each) and evidence per section (activities, skills, tools, certs) against the brief and the job's must-haves. **Hard caps are enforced in code**, so over-production stops here. Employers beyond the bullet cap stay listed as header-only entries. |
| 3a | Write, wave 1 (parallel) | default (Sonnet) | Experience (one call per role: achievements, outcomes, business impact), skills and tools, education and certs. Each sees only its selected evidence, the brief and that section's block syntax. |
| 3b | Write, wave 2 | default (Sonnet) | Professional profile and competencies, written after wave 1 so they cannot claim what the experience section does not support. |
| 4 | Assemble | none (code) | Order by structure guide, fill `{{contact}}`, `validateDraftMarkdown`, `fact-check.ts`, per-section word/bullet limits with one retry. |
| 5 | Review | `analysis` (Opus) | Cohesion against the brief. Lists every factual claim as supported / uncertain / unsupported against profile evidence. Unsupported claims are removed. |
| 6 | Land | none (code) | `createDraft` into the desk. The owner accepts or discards in the existing `DraftReview`. Nothing overwrites a live document. |

## Known constraints

- `createDraft` refuses if a draft already exists, and accepts only `cv` or untyped documents. The Land stage must handle "draft exists" (ask to discard or open it).
- A job holds at most 10 desk documents (`src/modules/writing-desk/schema.ts`).
- The desk stores Markdown, not the legacy JSON, so nothing from `CVDocumentContent` carries over.

## Stored selection (the contract Phase 3 consumes)

`CvGeneration.selection` (Json, parsed by `parseSelection` / `CvSelectionSchema` in `src/modules/cv-generation/schema.ts`; null when absent or unreadable). A run stores:

```ts
{
  mode: 'model' | 'fallback',
  employers: Array<{              // THE work history: one entry per employer, newest first, one timeline
    key: string                   // stable: normalised company name slug ("unity")
    company: string               // the most frequent spelling across its roles (a properly cased one beats all-lowercase)
    latestTitle: string           // title of the most recent role, exactly as in the profile; the CV heading
    start: string | null          // BOUNDS ONLY, for ordering: earliest start, ISO YYYY-MM-DD. NOT for display
    end: string | null            // null = any role current. NOT for display
    stints?: Array<{ start, end }>  // THE DATES TO SHOW, oldest first: the roles' ranges merged only where they touch, overlap or sit within ~3 months; end null = present. Absent on rows stored before stints (read start/end as one stint)
    roles: Array<{ experienceId, title, start, end }>   // oldest first, each role's own dates
    progression: string | null    // built in code, oldest title first, neutral wording; null with one role
    relevance?: 1..5              // employers with bullets only (absent when headerOnly). The model's score; 1 when it gave none; derived from brief/requirement term matches in a rules run. An unreadable stored value reads as 3
    reason: string                // why the model picked it; '' when code did
    headerOnly: boolean           // true: company, latest title, dates, progression only, no bullets
    bullets: Array<{ id, label, reason, experienceId }>  // kept activities, best first; experienceId = the role it came from (provenance, fact-checking)
  }>,
  skills, tools, competencies, certifications, education, projects: Array<{ id, label, reason }>,
  dropped: Array<{ section, id, label, parentId?, why }>,   // activities: parentId = employer key; section 'employers' for employers dropped over the cap
  droppedTotal, notSelectedTotal?,
  uncovered?: string[]            // phase 3: Brief "emphasise" items that no kept activity or project supports; absent on older rows (reads as [])
  // legacy, empty on new rows: experiences, headerOnlyRoles, activities
}
```

Rules for the writer: render `employers` in order; an employer with `headerOnly: false` gets its bullets, one with `true` is one header line. The heading is `latestTitle` at `company`; its dates are the `stints` (e.g. `2015–2017, 2019–present`), **never a single overall span from `start` to `end`**: an employer someone left and returned to (Unity 2015-17, Blizzard 2017-19, Unity 2019-present) must not read as continuous next to the other. `progression` already renders the stints; show it as sub-text. Never rewrite or drop a title. Read the number of employers that show bullets through `employersWithBullets(brief)` (`schema.ts`), not the raw `brief.budgets.experiences` key: the key predates employers and is kept so stored briefs parse. Write each employer's description and bullets only from its `bullets`. Rows stored by phase 2 (before employers) have `employers: []` and use `experiences`, `headerOnlyRoles` and `activities` (keyed by experience id); they still parse and render in the log, and a run is cheap to repeat, so phase 3 only needs to read the new shape.

Caps (`caps.ts`): employers with bullets `MAX_EMPLOYERS` 4 (a current employer always one: with several current employers, any one picked meets the rule; if none is, the one with the most activities, then the earliest start, is forced in), header-only `MAX_HEADER_ONLY_EMPLOYERS` 4, further employers dropped (`over_cap`); `TOTAL_ACTIVITY_BUDGET` 14 split by `allocateBullets`, `MIN_ACTIVITIES_PER_EMPLOYER` 2, `MAX_ACTIVITIES_PER_EMPLOYER` 6.

## Stored assembled CV (the contract Phase 4 consumes)

`CvGeneration.assembled` (Json, parsed by `parseAssembled` / `CvAssembledSchema` in `schema.ts`; null on runs stored before Phase 3, on a run that did not reach Assemble, or when unreadable). Exposed as `CvGenerationView.assembled`.

```ts
{
  markdown: string          // the whole CV as a writing desk document, ending with a newline; the header holds the literal {{contact}}, never contact details
  sections: Array<{         // in document order; their markdown joined with blank lines is `markdown`
    id: string              // 'header' | 'profile' | 'competencies' | 'experience:<employerKey>' | 'earlier-experience' | 'tools' | 'skills' | 'certification' | 'education' | 'languages'
    kind: string
    employerKey?: string    // experience entries
    markdown: string        // includes the section's `## heading` (for experience, only the first entry carries it)
    bullets?: Array<{ text: string; sources: Array<{ id: string; kind: 'activity' | 'project'; snippet: string }> }>  // Phase 3d: an employer entry's bullets with the evidence each came from; absent on older runs
    model?: string          // the model that wrote it; absent when code rendered it
    tokens?: { input, output }
  }>
  warnings: string[]        // block validator warnings and fact-check.ts findings (warnings only; they never fail a run)
  checkNotes: string[]      // at most MAX_CHECK_NOTES (3) "worth a quick check" notes
}
```

Review (phase 4) reads `markdown` and `sections`; Land creates the draft from `markdown`, and the app substitutes `{{contact}}` when the owner accepts it. The log's Write entry carries one `sections[]` row per section (model, time, tokens, cost, retries, notes).
